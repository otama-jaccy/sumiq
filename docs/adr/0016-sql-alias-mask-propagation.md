# ADR-0016: 別名（AS）で改名された列にマスクを伝播する

- ステータス: Accepted
- 日付: 2026-08-18
- 関連: [ADR-0003](./0003-config-file-design.md)（設定ファイルの設計）、[ADR-0004](./0004-output-formats.md)（出力形式）、[ADR-0007](./0007-layered-merge-guards.md)（レイヤードマージの安全ガード）、[ADR-0009](./0009-mask-null-strength.md)（マスク方法の強度）、[ADR-0010](./0010-mask-pattern-dialect.md)（列名パターンの方言）、[ADR-0015](./0015-datasource-default-action-monotonic-for-all-layers.md)

## コンテキスト

マスクは Redash が返した結果の**列名**にしか照合されない（`internal/mask.Engine.resolve`）。
列名はクエリの書き方で決まるため、別名を付けた時点でルールがマッチしなくなる。

```sql
SELECT email AS contact FROM users
```

- 結果の列名は `contact`。`patterns: ["email"]` はマッチしない
- `default_action: none`（denylist 運用）ならそのまま素通り、`redact`（allowlist 運用）でも
  「`email` を隠す」という意図は消えて既定側の判定に落ちる

ADR-0010 と `.claude/rules/go-architecture.md` は「列名は sumiq が決めるものではない」ことを
既に認識していたが、**改名されたときにルールを追従させる仕組みが無かった**
（[#43](https://github.com/otama-jaccy/sumiq/issues/43)）。意図的な回避も、
`SELECT u.email AS user_contact` と書いただけの無自覚な事故も同じ経路で起きる。
sumiq が守るべきは後者である（README「not a security boundary」）。

## 決定

### 1. 検出したら伝播する。クエリを拒否しない

出力列に適用する方法を、その列名への直接マッチと、由来になりうる列名へのマッチのうち
最も強いものにする。既存の「複数のルールがマッチしたら強い方が勝つ」規則
（ADR-0003 §7、ADR-0009）の自然な拡張として実装し、`partial` 同士は
`partialSpec.tighten` で「どちらも残す部分」だけを残す。

**由来については「マッチしたルール」だけを見る（`Engine.matchedMask`）。** `resolve` は
マッチが無いとき `default_action` に落ちるため、由来にそれを使うと allowlist 運用では
ルールに挙がっていない由来がすべて `redact` を押し付ける。過剰近似（決定 3）で拾った
型名やテーブル名でも押し付けるため、式から作った列に `method: none` の穴を開けられなくなる。
「マッチしたルールは `default_action` より優先される」（ADR-0003 §7）にも反する。

**別名の側に `method: none` を書いても伝播は打ち消せない。** `email` にルールが
マッチする限り `stronger(none, redact) = redact` になる。伝播を止める手段は許可リスト
（決定 4）だけに一本化した。2つの止め方があると、事故のときにどちらで外れたのかを
設定から追えない。

### 2. SQL の解析は自前の軽量トークナイザで行う

外部 SQL パーサ（vitess / pingcap parser 等）は採らない。

- Redash が繋ぐ方言（BigQuery / Athena / Presto / MySQL / PostgreSQL）を単一のパーサでは
  覆えず、パース失敗＝実行拒否が頻発する
- `*` の展開には結局スキーマカタログが要る。sumiq はそれを持っていない
- `go.mod` に依存を足さない

`internal/sqlalias` は `config` も `redash` も import しない葉パッケージとして置く。
許可関数は名前（`[]string`）だけを受け取る。

### 3. 過剰近似で設計する。正確な lineage は目指さない

スキーマが無いため、正確な列レベル lineage は原理的に解析できない。そこで
**取りこぼさないこと**を優先し、余計に拾うことは許す。

- 項目の中に現れた識別子は、キーワード表で落とせないものをすべて由来として拾う。
  型名（`CAST(email AS varchar)` の `varchar`）やテーブル名が混ざることがある
- キーワード表には**型名を載せない**。`date` / `text` のように列名と綴りが同じ語を
  落とすと伝播が消えるため、「余計に拾う」側に倒す
- 単純な列参照（`col` / `t.col`）ではキーワード表を使わない。`SELECT date AS d` の
  `date` は列として読む
- スコープを潰す。別スコープの同名の別名は同じものとして扱う

過剰マスクの原因を追えるように、`mask.Summary.ColumnMask.Via` に伝播元を持たせ、
`internal/output` の通知に出す。

**キーワードを「区切り」としても使う場所には注意が要る。** `FROM` は句の始まりでもあり、
`extract(year FROM ts)` / `trim(both ' ' FROM s)` / `substring(s FROM 1)` では引数の区切りでもある。
サブクエリのテーブル名を拾わないために「`FROM` の直後は列名ではない」と決めると、
引数の区切りの後ろにある**本物の列名を落とす**。この向きの間違いは過剰近似では
救われない（`/code-review` で検出）。括弧を開いたのが関数呼び出しかどうかで区別する。

### 4. 伝播を止められるのは「関数名」の許可リストだけ

`SELECT count(email) AS n` の `n` まで `redact` になるのを避けるため、
`masking.propagation_exempt_functions` を設ける。許可関数の呼び出しの内側にだけ現れた
識別子を閉包に入れない（祖先に許可関数があるかで見る）。

**列名ではなく関数名で切る。** 列名で切ると「この列は伝播させない」という指定になり、
ADR-0010 の方言（グロブ / `regex:`）を持ち込むことになる。`count*` が
`count_raw_emails` のようなユーザ定義関数まで通す事故は、`method: none` に `regex:` を
許さないのと同じ理由で避けたい。関数名は**完全一致・大文字小文字無視・修飾なし**のみで
照合する。

**既定は空。`count` も組み込みでは許さない。** 設定に書いていない弱化が既定で効いていると、
事故のときに「なぜ外れたか」を設定から追えない。

止まるのは伝播だけで、出力列名への通常の照合と `default_action` はそのまま効く。
`default_action: redact` の allowlist 運用では `n` は `redact` のままで、通したければ
他の列と同じく `method: none` の穴を明示的に開ける（`SELECT 1 AS n` でも同じことであり、
伝播の結果ではなく allowlist 運用そのもの）。

止めた事実は通知に出す。**通知には関数名と列名の両方が要る**ため、
`ColumnMask.Exempted` は列名の並びではなく `[]sqlalias.Exemption`（関数名 + 列名）にした。
許可リストに複数の関数を書いたとき、どれが効いたかは弱化の原因そのものになる。
許可関数の引数がさらに別名だった場合（`count(contact)` の `contact` が `email` 由来）は
閉包まで広げる。広げないと、実際に弱化が起きた列を通知に出せない。

### 5. 判定不能は3つに限り、既定は実行拒否（`alias_guard`）

次の3つを判定不能とする。

1. 字句として読めなかった（引用符・コメント・括弧が閉じていない、方言で終端が変わる
   文字列リテラル、複数ステートメント）
2. `SELECT` が1つも見つからない（非 SQL のクエリランナー、`SHOW` / `CALL`）
3. 出力名を辿れない改名がある。次のどちらか
   - 別名も単純な列参照も無い式があり、結果列と位置でも対応付けられない
   - 列別名リスト（`WITH q(c) AS (...)` / `(...) AS x(c)` / `CROSS JOIN UNNEST(arr) AS t(v)`）で
     出力列を丸ごと改名している。改名後の名前が内側の SELECT のどこにも現れず、
     位置で対応させるには「どの CTE / 派生テーブルの何番目か」を辿る必要があるため、
     スコープを潰す解析では追えない

3 の1つ目は「由来を持つ項目」に限る。`count(*)` や定数のように伝播するものが無い項目は、
出力名が分からなくても構わない。また次の2つは対象外にする。

- **select list の中のスカラーサブクエリ。** 外側の項目が内側の識別子まで参照列として
  拾っているため、内側の出力名が分からなくても由来は落ちない
- **出力列が外側から名前で引かれない SELECT。** `WHERE x IN (SELECT lower(email) FROM u)` の
  ような結果列にならないサブクエリまで拒否すると、ごく普通の SQL が既定で通らなくなる。
  CTE の本体と FROM 句の派生テーブルだけを対象にする（`/code-review` で検出）

`SELECT * FROM users` は判定不能にしない。`*` が展開する列は改名されずに元の名前で返るため、
従来どおりの名前一致で正しくマスクされる。危険なのは「内側で改名 + 外側で `*`」だが、
これは改名後の名前が返るので閉包で拾える。

判定不能のときの扱いはデータソース単位の `alias_guard` が決める。

- `strict`（未指定の既定）= エラーで実行を拒否する。解析はネットワークに依存しないため、
  **Redash に一切リクエストを飛ばさない**（`mask.New` を `client.Execute` より前に
  置いてあるのと同じ理由）
- `off` = 判定不能でも実行する。伝播そのものは止めない（解析できた範囲では効く）。
  判定不能だったことは毎回 stderr に警告として出す

**`off` はレビュー済みの共有ファイル（`sumiq.yaml`）にのみ書ける。** `method: none` と
同じ扱いで、マスクを弱める指定はレビューの対象でなければならない（ADR-0007）。
検査は畳む前のレイヤごとの指定に対して行う。畳んだ後の値を見る検査では、名前の勝ち負けと
項目ごとの引き継ぎ（`mergeDataSource`）を経て、レビューされないファイルの `off` が
共有設定の定義に紛れ込む。

グローバル既定は設けない。`SELECT` を読めるかどうかはデータソースの性質そのもので、
全体に掛ける意味を持たない。

### 6. 判定不能をどう扱うかの決定は `internal/mask` に1つだけ置く

`alias_guard` を `internal/app` でも読んで判定すると、利用者から見て同じ状況なのに、
どちらの検査が先に効いたかで文言が変わる。実際にそう書いたところ、`off` のときに
「位置対応の不一致」だけ警告が出ないという穴もできた（`/simplify` で検出）。

`internal/app` は次の2つを使うだけにし、`alias_guard` を読まない。

- `Engine.PrecheckAlias`: ネットワークに出る前の検査（`strict` なら実行を拒否する）
- `Summary.AliasUndetermined`: 実行後に警告を出すための理由

結果列と突き合わせて初めて分かる理由（位置対応が使えない）は `Apply` が同じ規則で判定する。

### 7. 位置対応は結果列と突き合わせる時点で判定する

別名の無い式の結果列名は DB が決める（`_col0` / `f0_` など）。トップレベルの select list に
`*` / `t.*` が無く、項目数と結果列数が一致するときだけ、結果列と項目を位置で対応させる。
項目数は SQL から分かるが結果列数は実行するまで分からないため、この判定は
`Engine.Apply` の中で行う。`strict` ならそこでエラーになる。

### 8. `Apply` の引数に解析結果を必須で足す

```go
func (e *Engine) Apply(res *redash.Result, a *sqlalias.Analysis) (*redash.Result, Summary, error)
```

省略可能な形（別メソッド・オプション・`nil` を空の解析として扱う）にしない。
渡し忘れをコンパイルエラーにする。渡し忘れると別名の列のマスクが黙って外れ、
出力を見てもそれが分からない。`nil` を渡した場合も実行時エラーにする。

`map[string][]string` 等への詰め替えもしない。詰め替えそのものが由来を落としうる経路になる
（`.claude/rules/go-architecture.md`「ここで型を詰め替えない」と同じ理由）。

### 9. 通知に弱化を出す（ADR-0004 §5 の3行を4行に増やす）

```
Masked: contact (redact, email 由来)
Dropped: --
Exempted: n (none, count が email の伝播を止めた)
Rows: 342
```

`Exempted` は該当が無くても `--` を出す。ADR-0004 §5 が「マスクされた列が無いことと、
まだ結果を見ていないことは区別できない」として3行を必ず出しているのと同じ理由で、
**弱化が起きた回と起きなかった回が区別できなければ通知の意味が無い。**

`Summary.Dropped` は列名（`[]string`）ではなく `[]ColumnMask` を返すように変えた。
伝播で消えた列は、なぜ消えたのかを出力から確かめられない。

## 結果

**得られるもの**

- 別名を付けるだけでマスクが外れる穴が塞がる。`AS`、`AS` 省略形、CTE、サブクエリ、
  `UNION` の各枝をまたいで追える
- 追えなかったことが既定で実行拒否になり、しかもネットワークに出る前に止まる
- 弱化の経路が「共有ファイルに書かれた許可関数」1つに集約され、通知で毎回見える

**支払うコスト**

- **過剰マスクが起きる。** 型名やテーブル名を由来として拾い、スコープを潰すため、
  身に覚えのない列が伏せられることがある。原因を追う手段は `Via` の通知だけになる
- **既定 `strict` は破壊的変更。** 非 SQL のクエリランナーを繋いだデータソースは
  `alias_guard: off` の追加が要る。移行期間として警告だけ出す案は、警告は無視されるので
  採らない（ADR-0015 で同じ理由により却下している）
- **列別名リストを使うクエリが拒否される。** Presto / Athena で一般的な
  `CROSS JOIN UNNEST(arr) AS t(v)` も含む。内側で `AS` を使う形に書き換えるか、
  そのデータソースを `alias_guard: off` にするしかない
- **自前トークナイザの方言差を抱え続ける。** 文字列リテラルの中のバックスラッシュのように
  方言で終端が変わる書き方はエラーにするしかない
- **許可リストの安全性はチームが判断する。** `count` は件数しか出ないが、
  `min` / `max` / `sum` / `avg` は行数の少ないグループで元の値そのものになる
  （1行なら `sum` は値と等しい）。sumiq 側で「安全な関数」を判定することはできない
- **`Apply` のシグネチャ変更**により、結果をマスクする呼び出しはすべて SQL の解析結果を
  持ち回る必要がある

**採用しなかった選択肢**

- **外部 SQL パーサを使う。** 方言を覆えず、`*` の展開にスキーマカタログが要る（決定 2）
- **別名を検出したらクエリを拒否する。** `AS` は日常的に使うため運用が回らない。
  伝播なら既存のマスク規則の拡張で済む
- **列名の許可リストで伝播を止める。** ADR-0010 の方言を持ち込むことになり、
  `method: none` に `regex:` を許さない判断と矛盾する（決定 4）
- **`count` を組み込みで許す。** 設定に書かれていない弱化が既定で効く状態を作る（決定 4）
- **`alias_guard` のグローバル既定を設ける。** 非 SQL かどうかはデータソースの性質であり、
  全体に掛ける意味がない（決定 5）
- **判定不能を警告だけにして実行を続ける（既定）。** 警告は無視される
- **由来にも `default_action` を効かせる。** Issue #43 は
  `stronger(resolve(c), resolve(s) for s in closure(c))` と書いていたが、これでは
  allowlist 運用で `method: none` の穴が塞がる（決定 1）

## 未決事項

1. **許可リストに何を書くかはチームの判断になる。** `min` / `max` / `sum` / `avg` の
   危険性は README に書いたが、sumiq が止める仕組みは無い
2. **許可リストはデータソース単位にスコープできない。** `masking.rules` には
   `data_sources` があるのに、許可リストは全データソースに効く。1つのデータソースの
   都合で書いた抜け道が本番のレプリカにも効く。`alias_guard` をデータソース単位にした
   のと同じ非対称が残っている（`/simplify` で検出）。要求が出たら
   `masking.rules` と同じ形のスコープを足す
3. **ユーザ定義関数が組み込みと同名でも区別できない。** `count` という名前の UDF を
   定義すれば中身が何であれ伝播が止まる。完全一致・修飾なしのみ受け付けることで面を
   狭めているが、原理的な穴としては残る
4. **スコープを潰すことによる過剰マスク。** 別スコープの同名の別名が混ざる。
   `Via` で原因を追えるようにして様子を見る
5. **MySQL の `ANSI_QUOTES` が無効なときの `"..."`** は文字列リテラルだが、識別子として
   読んでいる。中身が列名の候補に増えるだけなので過剰側に振れる
6. **引用識別子の中の閉じ記号の打ち消し方も方言で違う。** 2つ並べる形（PostgreSQL の
   `""`、MySQL のバッククォート2つ、SQL Server の `]]`）で読んでいるが、BigQuery の
   引用識別子は「文字列リテラルと同じエスケープ列」を使う（バックスラッシュで打ち消す）。
   識別子名にこれらの記号を含めるのは稀なため、方言差はエラーにせず2つ並べる形に寄せた
7. **BigQuery の三重引用符（`'''...'''`）は明示的に扱っていない。** 中に引用符を
   含まなければ、標準 SQL の「引用符2つ＝引用符そのもの」として読んだ終端位置が
   三重引用符の終端と一致するため、たまたま正しく読める。中に引用符を含む場合は
   トークナイズに失敗し、判定不能として実行を拒否する（fail-closed）。`'''` は
   PostgreSQL でも妥当な並び（`'` + 打ち消された `'`）であり、三重引用符として読む
   実装に変えると今読めているクエリが読めなくなるため、曖昧なまま片方に倒さない
8. **キーワード表の載せ忘れ・載せ過ぎ。** 載せ忘れは過剰マスク（安全側）、載せ過ぎは
   伝播の取りこぼし。窓関数の句（`range` / `rows` / `filter`）と綴りが同じ列名を
   式の中で使うと伝播が落ちる

## 参考

- [Issue #43](https://github.com/otama-jaccy/sumiq/issues/43)、[PR #44](https://github.com/otama-jaccy/sumiq/pull/44)
- PostgreSQL: [Lexical Structure](https://www.postgresql.org/docs/current/sql-syntax-lexical.html)
  — `standard_conforming_strings` は 9.1 以降 `on` が既定で、バックスラッシュの打ち消しは
  `E'...'`（エスケープ文字列）でだけ有効。通常の文字列で引用符を表すのは引用符2つ。
  dollar-quote のタグは「`$` を含まない引用符なし識別子」と同じ規則で省略可能、`$1` は
  タグにならない。引用識別子の中の `"` は2つ並べる
- MySQL: [String Literals](https://dev.mysql.com/doc/refman/8.4/en/string-literals.html)
  — バックスラッシュの打ち消しは既定で有効（`NO_BACKSLASH_ESCAPES` で無効化）。
  引用符2つも使える。`ANSI_QUOTES` が無効なとき `"..."` は文字列リテラル
- BigQuery: [Lexical structure and syntax](https://cloud.google.com/bigquery/docs/reference/standard-sql/lexical)
  — クォート付き文字列でバックスラッシュのエスケープ列が有効、`r'...'` は raw 文字列、
  `b'...'` はバイト列。引用識別子はバッククォートで囲み、エスケープ列は文字列リテラルと同じ
- Trino: 引用符2つで引用符を表し、バックスラッシュによる打ち消しは扱わない
  （[trinodb/trino#7784](https://github.com/trinodb/trino/issues/7784) が BigQuery の

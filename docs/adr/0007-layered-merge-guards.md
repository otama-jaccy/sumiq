# ADR-0007: レイヤードマージの安全ガード

- ステータス: Accepted
- 日付: 2026-08-14
- 関連: [ADR-0003](./0003-config-file-design.md)（設定ファイルの設計）

## コンテキスト

[ADR-0003](./0003-config-file-design.md) は探索順（§2）とマージの方針（§7）を決めたが、
実装してみると **決まっていない分岐が多数残っていた**。#2 で埋めた判断を記録する。

ADR-0003 §7 が守りたい性質は1つだけである。

> マスクは安全装置であり、ローカル設定で共有設定を弱められる構造にしてはならない。

問題は、この性質を破る経路が §7 が挙げた3つ（和集合 / 追加のみ / 最も強い方が勝つ）
だけではなかったこと。実装中とセルフレビューで、**同じ性質を別の道から破る経路が
6つ見つかった**。以下はいずれも、規則を1つ足すだけでは塞がらなかったものである。

| 経路 | どう弱まるか |
| --- | --- |
| ユーザ設定に `method: none` | §7 は「共有ファイルにのみ」と書いたが、`~/.config` は共有ファイルではない |
| 環境変数で `default_action` を下げる | ファイルの規則を環境変数に適用しないと素通りする |
| 別名で同じ `id` を指す | 名前の差し替えを禁じても、`prod` を足して同じ接続先を引ける |
| サブディレクトリに `sumiq.yaml` を置く | 「近い方が勝つ」だとルートのマスクルールが全部消える |
| データソース定義を項目単位で上書き | 構造体を丸ごと差し替えると、書いていない `default_action` が消える |
| `api_key_command` をコミット | 秘密は漏れないが、クローンしただけで任意コマンドが走る |

## 決定

### 1. 「レビュー済みかどうか」を判定の単位にする

ADR-0003 が本当に区別しているのは「共有 / ローカル」ではなく
**「git 上でレビューされるか」** である。制約はすべてこの述語1つに集約する。

| レイヤ | レビュー済み |
| --- | --- |
| 埋め込みデフォルト | — |
| `~/.config/sumiq/config.yaml` | **いいえ** |
| `<repo>/sumiq.yaml` | はい |
| `<repo>/sumiq.local.yaml` | いいえ |
| `--config` で指定したファイル | はい |
| 環境変数 / コマンドライン引数 | いいえ |

**ユーザ設定をレビュー対象外に含めるのが要点。** ADR-0003 §7 は
「`method: none` は共有ファイルにのみ書ける」と書いており、`~/.config` は
共有ファイルではない。`method: none` は `default_action: redact` に穴を開ける
唯一の手段なので、レビューされない場所から書けてはならない。

`--config` はレビュー済みとして扱う。探索（§2 の 2〜4）を丸ごと置き換えるもので、
CI から共有ファイルを直接指す使い方が主用途になる。ローカル扱いにすると
`sumiq --config ./sumiq.yaml` が自分の共有設定で落ちる。ADR-0003 が
「これはセキュリティ境界ではない」と置いているとおり、防ぐ相手は事故であって、
自分でパスを渡す利用者ではない。

### 2. 環境変数レイヤもファイルと同じ形に組み立てる

環境変数を専用の経路にせず、`Config` 1枚に組み立ててから同じマージに通す。
別扱いにすると `SUMIQ_MASKING_DEFAULT_ACTION=none` がマスク解除の逃げ道になる。

**リスト（`data_sources` / `masking.rules`）は環境変数から設定できない。**
1つの文字列に押し込む記法を用意すると、マスクルールをシェル変数から書けてしまい、
レビューを迂回する経路そのものになる。

### 3. データソースは名前と `id` の両方を守る

- 同一ファイル内の名前の重複はエラー（書き間違い）
- レビュー済み設定がレビューされない設定の定義を上書きするのは**許す**。
  これは §2 の「下が勝つ」であり、禁じるとユーザ設定に名前を1つ置いただけで
  その名前を使う全リポジトリが動かなくなる
- 逆向き（レビューされない設定がレビュー済みの定義を差し替える）はエラー
- **レビューされない設定は、レビュー済みの `id` に別名を付けられない**

最後の1つが要る理由は、マスクの強さが**名前ではなく接続先に紐づく**こと。
共有設定が `analytics (id: 3)` を `default_action: redact` に上げていても、
ローカルから `prod (id: 3)` を足せば、グローバル既定のまま同じ接続先を引ける。
`data_sources: [analytics]` で紐づけたルールも名前で照合するため効かない。
名前の差し替えを禁じるだけでは足りなかった。

### 4. 同名データソースの再定義は項目ごとに畳む

構造体を丸ごと差し替えてはならない。ルートで `analytics` に
`default_action: redact` を付け、`packages/etl/sumiq.yaml` で同じ名前に
`auto_limit: false` だけを足す（ADR-0003 §10 が Oracle / SQL Server 向けに
勧めている書き方）と、書いていない `default_action` が黙って消える。

### 5. 遡って見つけた設定ファイルは全部重ねる

ADR-0003 §2 は「カレントから git root まで遡って探索する」と書いているが、
複数見つかったときの扱いを決めていなかった。**全部を弱い順（遠い方が先）に重ねる。**

「近い1枚だけを読む」を選ぶと、モノレポでリポジトリルートにマスクルールを置き、
`packages/etl/sumiq.yaml` に `timeout` だけを書いた瞬間に、ルートのマスクルールが
全部消えて `default_action` も埋め込みデフォルトに戻る。エラーも警告も出ない。
**近さで勝敗を決めるのは、弱化を黙って通す経路そのものだった。**

全部重ねれば `masking.rules` は和集合になり、近いファイルはスカラーを上書きするだけになる。

**git リポジトリの外では遡らず、カレントディレクトリだけを見る。** 上限が無いまま
遡ると、ホームディレクトリに置き忘れた `sumiq.local.yaml` を黙って読んでしまう。

### 6. `api_key_command` も git 管理下のファイルには書けない

ADR-0003 §5 は `api_key` について「git の管理下にあるファイル由来なら停止する」と
決めたが、`api_key_command` を対象にしていなかった。**両方を対象にする。**

値そのものは秘密ではない。しかしこれは**実行されるコマンド**であり、コミットできると
`git clone <未信頼> && cd && sumiq query ...` でそのリポジトリの `sumiq.yaml` に
書かれた任意のコマンドが走る。ADR-0003 の「これはセキュリティ境界ではない」は
利用者自身が迂回することを指しており、未信頼のリポジトリ内容が実行される経路は
想定していない。

ADR-0003 自身の記述とも整合する。`api_key_command` が現れるのは §4 の
**ローカルファイル**のスキーマだけで、§3 の共有ファイルには含まれていない。

### 7. `api_key` と `api_key_command` の優先順位はレイヤの強弱で決める

ADR-0003 §5 は取得元を 1. 環境変数 2. `api_key` 3. `api_key_command` と
番号付きで挙げているが、これは**「3経路を用意する」という列挙であって
優先順位の規定ではない**と読む。優先順位は §2 の「下が勝つ」に従う。

両者は組で差し替える。同一ファイルに両方書かれていたらエラーにする
（どちらを使うつもりだったのか決められないため）。

### 8. ゼロ値になる指定は書けたことにしない

各フィールドのゼロ値は「未指定」を意味する（ADR-0005 の実装方針）。
そのため `timeout: 0s` や `SUMIQ_QUERY_MAX_ROWS=0` は、**書いても下のレイヤの値が
そのまま残る。** 利用者から見れば設定が黙って別の値に差し替わる。

`Duration` の `0` と `max_rows` の `0` 以下は受け付けない。

`max_rows` は `int` で受けているためファイル側で `0` と未指定を区別できず、
そちらは負値だけを弾く。この非対称は型の帰結として受け入れる。

### 9. 制約を破ったエラーには、必ず「相手側の出どころ」を書く

`default_action` を緩める指定を弾くとき、**厳しい側がどのファイル由来かを必ず添える。**
これが無いと、利用者は名前の挙がったファイルを開いて緩い値を見つけるだけで、
なぜ怒られたのか分からない。厳しい値が自分のユーザ設定由来のときが最悪で、
リポジトリの中を探しても原因が見つからない。

## 結果

**得られるもの**

- 「レビューされない設定からマスクを弱める」経路が、判定述語1つに集約された。
  規則を足すときは、それが単調かどうかだけを確かめればよい
- マスクの強さがデータソースの**名前ではなく接続先**に紐づくことが保証される
- サブディレクトリに設定を置いてもマスクは強くしかならない
- 秘密も、秘密を取るコマンドも、コミットされた状態では使えない

**支払うコスト・受け入れる制約**

- **設定が厳しすぎて動かない場面が出る。** 特に §3 の `id` の規則は、
  ユーザ設定にデータソースを1つ書くだけで、同じ `id` を別名で使う
  リポジトリが動かなくなる。逃げ道は用意していない
- **マージ規則が増え、実装が読みにくくなった。** 規則の一覧を
  `internal/config/merge.go` 冒頭の doc comment に置いて緩和しているが、
  1か所を読めば分かる状態ではなくなっている
- `api_key_command` を共有ファイルに置けないため、チーム共通の取得方法
  （全員が `op read op://Team/redash/credential` を使う等）を共有できない。
  各自が `sumiq.local.yaml` に書く必要がある
- 遡って全部重ねるため、読まれるファイルが増えて「どの設定が効いているか」が
  追いにくくなる。`Resolved.Files()` で読んだファイルを列挙できるようにしたが、
  それを見せるコマンドはまだ無い

**採用しなかった選択肢**

- **「近い方が勝つ」（§5）。** どこに何を書いたかが追いやすく、実装も単純だが、
  ルートのマスクルールを無警告で消せるため却下した
- **データソース名の再定義を一律エラーにする（§3）。** 最も単純で fail-closed だが、
  ユーザ設定に名前を1つ置くだけでリポジトリが動かなくなるため却下した
- **`Reviewed()` を git の追跡状況で判定する（§1）。** 「レビュー済み」の定義として
  はファイル名より正確だが、まだコミットしていない `sumiq.yaml` を書いている最中に
  落ちるようになる。未決事項に残す
- **`--config` をレビュー対象外として扱う（§1）。** より fail-closed だが、
  CI から共有ファイルを指す使い方を壊すため却下した

## 未決事項

### `default_action` を緩める指定は、エラーにすべきか厳しい方を残すべきか

**現在はエラー。** #2 の受け入れ条件が「緩める指定はエラー」と明示していたため
そのまま実装したが、セルフレビューで**3回**指摘された。

問題は次の場面である。ユーザが自分の `~/.config/sumiq/config.yaml` に
`masking: {default_action: redact}` と書いて既定を固くすると、
**ADR-0003 §3 のサンプルどおり `default_action: none` を持つ共有設定の
リポジトリで `sumiq` が一切動かなくなる。** しかも `none` を書いたのはチームであって
ユーザではない。

fail-closed の性質は「厳しい方を黙って残す」でも同じように満たせる。
エラーにする利点は「書いた設定が無視されない」ことだが、
代償はリポジトリ単位の全面停止である。

エラーメッセージに厳しい側の出どころを書くようにしたのは緩和にすぎない。
**受け入れ条件を変える判断になるため、#2 では変えていない。**

### `Reviewed()` の判定をファイル名から git の追跡状況に変えるか

現在は `sumiq.yaml` という名前でありさえすれば、コミットされていなくても
`method: none` を書ける。同じ内容が `sumiq.local.yaml` なら弾かれる。
**リネームだけで保証を迂回できる。**

同じパッケージの `gitTracked` で本当に判定できるが、そうすると
書いている最中の `sumiq.yaml` が信頼されなくなる。

### `sumiq.local.yaml` の `api_key_command` による任意コード実行

§6 で git 管理下のファイルは塞いだが、gitignore された `sumiq.local.yaml` を
リポジトリに同梱して配る経路は残る。確認プロンプトを出すか、実行できる
コマンドを制限するか。

### 複数の Redash インスタンス

§3 の `id` の規則は「`id` が同じなら同じ接続先」を前提にしている。
`data_source_id` は Redash インスタンスごとの値なので、接続先が増えたら
成り立たない。ADR-0003 の未決事項「プロファイル機能」と同時に決める必要がある。

## 参考

- [git-ls-files Documentation](https://git-scm.com/docs/git-ls-files) —
  `--error-unmatch` は "If any \<file\> does not appear in the index, treat this as an error (return 1)"。
  **1 だけが「追跡外」を意味する。** 他人所有のチェックアウト（dubious ownership）や
  壊れた index は 128 で落ちるため、これを追跡外に倒すと検査が fail open する。
  手元の git 2.39.5 で 0 / 1 / 128 を実測して確認した
- [git Documentation — `--literal-pathspecs`](https://git-scm.com/docs/git#Documentation/git.txt---literal-pathspecs) —
  "Treat pathspecs literally (i.e. no globbing, no pathspec magic)"。
  パスを pathspec として渡す以上 glob 解釈の対象になる。
  なお `proj[1]` のようなディレクトリ名でも実測では `--error-unmatch` は 0 を返した
  （`ls-files` が index の項目と literal に突き合わせるため）。ドキュメント化された
  挙動ではないので依存しない
- [os/exec — `Cmd.WaitDelay`](https://pkg.go.dev/os/exec#Cmd) —
  "bounds the time spent waiting on two sources of unexpected delay in Wait: a child
  process that fails to exit after the associated Context is canceled, and a child
  process that exits but leaves its I/O pipes unclosed"。
  `CommandContext` の kill だけでは孫プロセスがパイプを握ったまま `Output()` が
  止まり続けるため、締切を守るには `WaitDelay` が要る

# ADR-0004: 出力形式を table / json / csv の3種とし、CLI 引数で選択する

- ステータス: Accepted
- 日付: 2026-08-14
- 関連: [ADR-0001](./0001-layered-cli-architecture.md), [ADR-0003](./0003-config-file-design.md)

## コンテキスト

[ADR-0003](./0003-config-file-design.md) は出力形式を未決事項として範囲外に置いた。これを決める。

要件は `table` / `json` / `csv` の3種をコマンドライン引数で選べること。

決めるべき細部が複数ある。

- フラグ名と既定値
- マスク結果を各形式でどう表現するか（特に `drop` と `null`）
- どの列がマスクされたかを利用者にどう伝えるか
- `on_exceed: error` に達したときの出力の扱い

## 決定

### 1. フラグは `--format`。短縮形は設けない

```bash
sumiq query -d analytics --format json "SELECT id, email FROM users"
```

kong の `enum` タグで検証する。

```go
Format string `enum:"table,json,csv" default:"table" help:"出力形式"`
```

**短縮形 `-f` は割り当てない。** SQL 系 CLI では `-f` は「ファイルからクエリを読む」の意味で広く使われており（`psql -f`）、`sumiq` でも近い将来 `--file` が欲しくなる可能性が高い。同様に `-o` は「出力先ファイル」として予約する。

後から短縮形を追加するのは非破壊だが、意味を変えるのは破壊的変更になる。曖昧な文字を先に消費しない。

### 2. 既定は常に `table`。TTY による自動切り替えはしない

パイプされているかどうかで形式を変える設計は採らない。`sumiq ... | less` が JSON になるのは驚きであり、挙動が文脈依存になるとデバッグしづらい。

ただし**装飾は TTY を見て落とす**。色付けと罫線は非 TTY では出力しない。形式は変えず、見た目だけ落とす。

`output.format` を設定ファイルに書いて既定を変えられる。優先順位は ADR-0003 の規則どおり、CLI 引数が最も強い。

### 3. マスク結果の表現を形式間で統一する

| method | table | json | csv |
| --- | --- | --- | --- |
| `redact` | `****` | `"****"` | `****` |
| `partial` | 残した部分 | 同左（文字列） | 同左 |
| `hash` | ハッシュ先頭N文字 | 同左（文字列） | 同左 |
| `null` | `NULL` | `null` | 空フィールド |
| `drop` | 列を表示しない | キーを含めない | ヘッダからも除く |

**`drop` は全形式でヘッダ・キーからも消す。** 値だけ空にして列名を残すと「取得したが空だった」と誤読される。

**`csv` では `null` と空文字列を区別できない。** これは CSV の制約であり回避しない。区別が必要な場合は `json` を使う。この制約はヘルプに明記する。

**型は保存しない。** Redash は列型を返すが、`hash` や `redact` を適用した時点で整数列は文字列になる。形式ごとに型を出し入れすると挙動が複雑になるため、**マスクされた列の値は常に文字列として出力する**。マスクされていない列は元の型を保つ。

### 4. `json` は「オブジェクトの配列」とする

```json
[
  {"id": 1, "email": "****@example.com"},
  {"id": 2, "email": "****@example.jp"}
]
```

`{"columns": [...], "rows": [...]}` 形式も検討したが、`jq` での扱いやすさを優先する。列順は SQL の結果順を保ってエンコードする（Go の map ではなく順序を保持した構造で出力する）。

### 5. マスク・打ち切りの通知は stderr に出す

```
$ sumiq query -d analytics --format json "SELECT id, email, memo FROM users" | jq .
Masked: email (partial), memo (redact)
Dropped: --
Rows: 342
```

**stdout はデータのみとし、メタ情報は一切混ぜない。** パイプ先を壊さないため。

これは必須の機能である。`redact` の `****` は見れば分かるが、**`hash` の出力は一見して本物の値と区別できず、`drop` された列は存在しないことすら分からない。** どの列にどのマスクが掛かったかを毎回明示する。

ADR-0001 で `Out` と `Err` を別の `io.Writer` として注入しているのは、この分離を実装レベルで保証するため。

### 6. 空の結果セット

- `table`: stdout に何も出さず、stderr に `Rows: 0`
- `json`: `[]`
- `csv`: ヘッダ行のみ

いずれも終了コードは 0。「結果が0件」はエラーではない。

### 7. `on_exceed: error` では stdout に何も書かない

行数超過でエラーにする場合、**部分的な出力を書いた後にエラーにしてはならない。** 途中まで出た結果を完全なものと誤認する事故につながる。

行数を検証してから書き始める。`max_rows` は 1000 前後の想定なので、全行をメモリに保持してから出力して差し支えない。ストリーミング出力は行わない。

### 8. `table` は標準ライブラリの `text/tabwriter` で実装する

外部依存を増やさない。整形はタブ区切りの左揃えで足りる。

**長い値の切り詰めは行わない。** マスク済みの値を切り詰めると更に誤読を招く。長いテキスト列があって表が崩れる場合は `json` か `csv` を使う、という方針にする。

## 結果

**得られるもの**

- `stdout` がデータのみになり、`| jq` や `> out.csv` が素直に機能する
- どの列がマスクされたかが毎回可視化され、`hash` や `drop` の存在を見落とさない
- 形式間でマスク表現が一致し、形式を変えても解釈が変わらない

**支払うコスト・受け入れる制約**

- `csv` では `null` と空文字列が区別できない
- マスクされた列の型情報が失われる（常に文字列になる）
- ストリーミング出力しないため、`max_rows` を大きくするとメモリを消費する。`max_rows` に上限を設ける必要が出るかもしれない
- `table` が長いテキスト列で崩れる。切り詰めないという判断の代償

## 未決事項

- `--output <file>` によるファイル書き出し（`-o` は予約済み）
- `--file <path>` による SQL のファイル読み込み（`-f` は予約済み）
- `jsonl` / NDJSON 形式（大量行をストリーム処理したくなった場合）
- `csv` の Excel 向け BOM 付与オプション
- `table` の最大列幅指定

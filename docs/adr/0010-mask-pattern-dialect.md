# ADR-0010: 列名パターンのグロブは `*` と `?` だけを特別扱いする

- ステータス: Accepted
- 日付: 2026-08-14
- 関連: [ADR-0003](./0003-config-file-design.md), [ADR-0009](./0009-mask-null-strength.md)

## コンテキスト

[ADR-0003](./0003-config-file-design.md) §3 は `masking.rules` の `patterns` について「既定でグロブ（大文字小文字を無視）。`regex:` 接頭辞で正規表現に切り替える」とだけ決めており、**グロブの方言までは決めていない。** #4 で適用エンジンを実装するにあたり、標準ライブラリの `path.Match` に委ねられるかを検討した結果、委ねられないと判断した。

`path.Match` / `filepath.Match` の構文は次のとおり（`go doc`、Go 1.25.5）。

```
term:
	'*'         matches any sequence of non-/ characters
	'?'         matches any single non-/ character
	'[' [ '^' ] { character-range } ']'
	c           matches character c (c != '*', '?', '\\', '[')
	'\\' c      matches character c
```

`filepath.Match` には加えて次の注意書きがある。

> On Windows, escaping is disabled. Instead, '\\' is treated as path separator.

ここから、そのまま使うと**マスクが黙って外れる**経路が3つ出る。

1. **`*` と `?` が `/` をまたがない。** 列名は `sumiq` が決めるものではなく、クエリの書き方でどうにでもなる（`SELECT ... AS "payload/user/email"` は多くの DBMS で通る）。`/` を含む列名があると `patterns: ["*"]` すらマッチしない
2. **`\` が打ち消しとして読まれる。** `\` を含む列名をそのままパターンに書くと、`\u` が `u` に化けて何にもマッチしない。**列名をコピーして貼ったパターンが、その列にマッチしない**
3. **`filepath.Match` は Windows で `\` の扱いが変わる。** 同じ設定ファイルが実行環境で違う結果になる

いずれも「マッチするはずのものがマッチしない」側の食い違いであり、マスクが弱まる方向にしか倒れない。マスクは安全装置であり、外れたことは出力を見ても分からない（ADR-0004 §5 がサマリを必須にしているのはこのため）。

残る問題が `[` である。`[` は文字クラスの開始としても、列名に含まれる文字そのものとしても読める。

- 文字クラスとして読むと、`data[0]` という列名を指すつもりで書いた `patterns: ["data[0]"]` が `data0` にマッチし、**当の列にはマッチしない**
- 文字そのものとして読むと、`col[0-9]` と書いて 10 列を指すつもりの指定が、`col[0-9]` という名前の列だけを指す

**どちらに倒しても、読み違えた側でマスクが外れる。**

## 決定

**グロブで特別な意味を持つのは `*` と `?` だけとし、他の文字は全て文字そのものとして照合する。`[` はエラーにする。**

- `*` は任意の並び（0 文字を含む）にマッチする。`/` も `\` も改行もまたぐ
- `?` は任意の1文字にマッチする
- `\` は打ち消しではない。`\` という文字そのもの
- `[` を含むパターンはエラーにし、`regex:` を使うよう促す
- パターン全体が列名と一致すること（部分一致ではない）を要求する
- **`regex:` も大文字小文字を無視する**（後述）
- **`regex:` は部分一致のままにする。ただし `method: none` には書けない**（後述）

`path.Match` / `filepath.Match` は使わず、パターンを正規表現に直して照合する。

### `[` をエラーにする理由

曖昧なものを黙ってどちらかに倒さない。`regex:` という逃げ道が既にあり、`regex:^data\[0\]$` とも `regex:^col[0-9]$` とも書ける。**どちらの意図も表現でき、しかも書いた側がどちらを意図したかが読んで分かる。**

エラーは `New` の時点、つまりクエリを投げる前に出る。設定を直すまで実行できないが、直せば意図どおりに動く。マスクが外れたまま実行されるより良い。

### `regex:` も大文字小文字を無視する

ADR-0003 §3 が大文字小文字の無視を明記しているのはグロブについてだけだが、正規表現にも同じ扱いを適用する。

同じ列が `email` で返るか `Email` で返るかは、クエリの書き方（`SELECT email AS Email`）と DBMS の識別子の畳み込みで変わる。ADR-0003 §7 の例に挙がっている `regex:^(first|last)_name$` は、列が `First_Name` で返った瞬間に効かなくなる。グロブでは掛かるのに正規表現では外れる、という差の方が事故になる。

区別が必要な場合は `(?-i)` を書けば戻せる。逃げ道は残っている。

### `regex:` は部分一致のままとし、`method: none` にだけ書けなくする

グロブを全体一致にした結果、**グロブは全体一致・`regex:` は部分一致**という非対称が生まれる。`regex:` 側を全体一致に揃えることはしない。正規表現の既定を曲げると、他のツールで通用する読み方が `sumiq` でだけ変わる。ADR-0003 §7 の例が `regex:^(first|last)_name$` と明示的に錨を打っているのも、部分一致を前提にした書き方である。

ただしこの非対称は、**`method: none` と噛み合ったときだけ危険な向きに効く。**

```yaml
masking:
  default_action: redact     # allowlist 運用
  rules:
    - patterns: ["regex:user_id"]
      method: none           # user_id だけ通したい
```

これは `user_id` に加えて `user_identity` / `user_id_email` / `hashed_user_id_secret` も素通しにする。書いた側は1列だけ通したつもりでいて、エラーも警告も出ない。

`method: none` は allowlist に穴を開ける唯一の手段であり（ADR-0003 §7）、**穴の大きさが読んで分かる形でなければならない。** そこで `method: none` のルールには `regex:` を書けないことにする。通す列はグロブで1つずつ挙げる。`patterns` はリストなので複数列も書ける。

他の method では部分一致がそのまま使える。広くマッチしすぎたときに起きるのは過剰なマスクであり、安全側に倒れるため。

## 検討したが採用しなかった選択肢

**`path.Match` をそのまま使う** — 標準の方言をそのまま使えるのが利点。採らなかったのは上述の3経路のためである。特に `\` の打ち消しは、`filepath.Match` の Windows での挙動と合わせて、**同じ設定が環境で違う結果になる**という性質が悪い。

**`filepath.Match` を使う** — `path.Match` より悪い。Windows で `\` の意味が変わる。

**`[` を文字クラスとして扱う（標準グロブに合わせる）** — 実装は済んでいた（#4 の実装中に一度書いた）が、`data[0]` のような列名を指せなくなる非対称が残る。標準に合わせる利点より、曖昧な指定を黙って通す欠点を重く見た。

**`[` を文字そのものとして扱う** — 列名は指せるようになるが、今度は `col[0-9]` と書いた側が黙って外れる。エラーにするより悪い。

**`\` を打ち消しとして残しつつ `/` の問題だけ直す** — `\` を含む列名という現実の入力に対して、パターンをそのまま書けない状態が残る。`patterns` に書くのは列名そのものであることがほとんどで、打ち消しが要る場面（`*` や `?` を含む列名）より、打ち消しが邪魔になる場面の方が多い。

**`regex:` も全体一致にして非対称を消す** — `method: none` の問題も同時に消える。採らなかったのは、正規表現の既定を曲げると他のツールで通用する読み方が `sumiq` でだけ変わるため。`regex:email` が `user_email` にマッチしないことを、書いた本人が気付ける保証がない。**過剰にマスクする側の食い違いなので事故にはならないが、驚きは残る。**

**`method: none` の `regex:` に錨（`^` と `$`）を必須にする** — 表現力を残したまま穴を塞げる。採らなかったのは、錨が効いているかの判定が構文だけでは決まらないため。`^a|b$` は `^` で始まり `$` で終わるが、`b` は錨が効いていない。`regexp/syntax` で構文木を辿れば正確に判定できるが、**「穴の大きさが読んで分かる」ことが目的なのに、判定そのものが読んで分からない。**

## 結果

**得られるもの**

- **列名をそのまま `patterns` に書けば、必ずその列にマッチする。** 列名に何が入っていても成り立つ
- `patterns: ["*"]` が全ての列にマッチする。allowlist を組むときの前提が崩れない
- 実行環境（OS）でマスクの結果が変わらない
- 曖昧な指定は実行前にエラーになり、黙って別の意味に解釈されない

**支払うコスト・受け入れる制約**

- **標準のグロブより狭い。** 文字クラス（`col[0-9]`）が書けず、`regex:` に切り替える必要がある。`sumiq` を触る人が別のツールの感覚で書くと、エラーを1回踏む
- **`*` や `?` を含む列名をグロブで指せない。** `regex:` を使う。`*` を含む列名は `col*` のようなパターンに巻き込まれるが、これは過剰にマスクする側なので許容する
- `regex:` の暗黙の大文字小文字無視は、正規表現に慣れた利用者にとって驚きになりうる。`(?-i)` で戻せることをドキュメントに書く必要がある
- **グロブと `regex:` で一致の範囲が違う。** 同じ意図を書いたつもりの `user_id` と `regex:user_id` が別の列集合に掛かる。`method: none` では後者を禁じたが、他の method では非対称が残る
- **allowlist に穴を開けるとき、列を1つずつ挙げることになる。** `regex:^(a|b|c)$` のようにまとめて書けない。冗長になるが、穴の一覧が読めば分かる形になる
- 方言を自前で持つ以上、その仕様はテストでしか担保されない

## 未決事項

- `patterns` が列名以外（テーブル名、型）に掛かる指定を持つべきか。現状は列名だけ

# ADR-0001: CLI とドメインロジックを分離したレイヤ構成を採用する

- ステータス: Accepted
- 日付: 2026-08-14

## コンテキスト

`sumiq` を Go の CLI ツールとして新規に作るにあたり、ディレクトリ構成と依存の向きを決める必要がある。

Go の CLI では、以下の失敗パターンが繰り返し観測されている。

- `main.go` にフラグのパースとビジネスロジックが同居し、ロジック単体のテストが書けない
- CLI フレームワーク（cobra 等）の型がドメイン層まで浸透し、ロジックのテストのたびにコマンドオブジェクトの組み立てが必要になる
- `cobra-cli` ジェネレータが生成する形をそのまま使い、パッケージレベル変数と `init()` にフラグ登録が散らばって、テスト間で状態が漏れる
- ロジックの途中で `os.Exit` を呼び、`defer` が実行されないうえテストから呼べない関数ができる

これらは後から剥がすコストが最も高い部類の負債であり、初期に方向を決めておく価値がある。

一方で、最初から `golang-standards/project-layout` の全体をなぞるのは過剰でもある。あれは公式標準ではなく、小さなツールに適用すると空のディレクトリが並ぶだけになる。

## 決定

以下のレイヤ構成を採用する。

```
sumiq/
├── cmd/sumiq/main.go     # エントリポイント。依存の組み立てと os.Exit のみ
├── internal/
│   ├── cli/              # コマンド定義。CLI フレームワークを知る唯一の層
│   ├── app/              # ドメインロジック。CLI フレームワークを import しない
│   └── config/           # 設定の読み込み
└── docs/adr/
```

依存の向きは `cmd → internal/cli → internal/app` の一方向とし、逆流させない。

あわせて以下を守る。

1. **`cmd/sumiq/main.go` は配線のみ。** 依存を組み立て、`internal/cli` を呼び、終了コードを `os.Exit` に渡して終わる。ロジックを置かない。
2. **`os.Exit` は `main` だけで呼ぶ。** それ以外の層はエラーを戻り値で返し、終了コードへの変換は最上位で一度だけ行う。
3. **`internal/app` は CLI フレームワークを import しない。** ここは `go test` から素の関数として叩ける状態を保つ。
4. **出力先は `io.Writer` として注入する。** `os.Stdout` を直接書かず、構造体または引数で受け取る。テストでは `bytes.Buffer` に差し替えて出力内容を検証する。入力が必要なら同様に `io.Reader` を注入する。
5. **パッケージレベルの可変変数を持たない。** フラグの格納先はコマンドごとの構造体に閉じる。
6. **`pkg/` は当面作らない。** 外部モジュールから import させたいものが実際に出てきた時点で検討する。それまでは全て `internal/` に置き、コンパイラによる import 禁止の恩恵を受ける。

構成は最初から全てを切るのではなく、実装の進行に応じて育てる。サブコマンドが増えるまでは `internal/cli` 内をフラットに保ってよい。ただし上記 1〜5 は最初から適用する。

## 根拠

- `internal/` は Go コンパイラ自身が外部からの import をブロックする唯一の仕組みであり、公開 API 面を意図せず固定してしまう事故を構造的に防げる。実装詳細を後から自由にリファクタできる。
- CLI フレームワークを `internal/cli` に閉じ込めることで、フレームワーク選定が可逆になる。差し替えが必要になっても書き換え範囲が 1 パッケージに収まる（ADR-0002 参照）。
- `io.Writer` 注入は Go の CLI で長く定着したパターンで、外部プロセスを起動する E2E テストなしに出力を検証できる。テストの実行速度と安定性に直結する。
- `cmd/` を薄く保つと、将来サブコマンドや別バイナリを追加する際に既存コードのリファクタが不要になる。

## 結果

**得られるもの**

- ドメインロジックがフレームワーク非依存になり、テーブルドリブンテストで素直に検証できる
- 出力の検証がインメモリで完結し、テストが速く壊れにくい
- フレームワーク選定を後から覆せる

**支払うコスト**

- 単一ファイルで済む規模に対してはパッケージ境界がオーバーヘッドになる。境界を跨ぐ型の定義が必要になる場面がある
- `internal/cli` と `internal/app` で似た構造体（フラグ用と入力用）が並ぶことがある。詰め替えの手間を許容する

**やってはいけないこと**

- `internal/app` に CLI フレームワークの型が現れたら、それは境界が壊れたサイン。即座に戻す
- 「一時的に」`os.Exit` をロジック側に置かない

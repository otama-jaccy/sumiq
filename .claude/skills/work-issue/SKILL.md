# Issue を実装して PR を出す

対象 Issue: **#$ARGUMENTS**

実装 PR と、設計ドキュメント更新 PR の **2本を別々に**出すのがこのスキルの目的。
片方が不要なら出さなくてよいが、**1本の PR に混ぜてはいけない**。実装のレビューと設計判断のレビューは観点も承認者も違う。

## 0. 事前チェック

以下を確認し、問題があれば作業を始めずユーザーに報告する。

- [ ] 作業ツリーがクリーンである（`git status`）
- [ ] `main` が最新である
- [ ] Issue #$ARGUMENTS が open である

`main` に直接コミットしない。

## 1. 文脈を読み込む

**実装を書き始める前に必ず読む。**

- [ ] `gh issue view $ARGUMENTS` で Issue 本文と受け入れ条件を取得する
- [ ] Issue が参照している ADR（`docs/adr/`）を読む
- [ ] **`.claude/rules/go-architecture.md` を読む**
- [ ] Issue の `Blocked by` に挙がった Issue が未完了なら、その旨をユーザーに伝えて判断を仰ぐ

`.claude/rules/go-architecture.md` は `paths: ["**/*.go"]` でスコープされているため、
**まだ `.go` ファイルが少ない段階では自動で読み込まれない可能性がある。** 明示的に読むこと。

読み終えたら `TaskCreate` で受け入れ条件をチェックリスト化する。1つ終わるごとに `TaskUpdate` で更新する。

## 2. 実装ブランチを切る

```bash
git switch -c feat/issue-$ARGUMENTS-<短いスラッグ>
```

## 3. 実装する

- 受け入れ条件を1つずつ満たす
- `.claude/rules/go-architecture.md` の禁止・必須事項は例外なく守る
- テストは受け入れ条件に書かれた観点を必ず含める
- コミットは論理単位で分ける。1コミット1目的

### 気づきは「その場で」記録する

実装中に以下に遭遇したら、**忘れる前にメモを取る**。後から思い出そうとしない。

- ADR の決定が実装してみると成り立たない、または曖昧だった
- ADR に書かれていない判断を自分で下した
- 同じ間違いを繰り返しそうな箇所（＝ rule に書く価値がある）
- Issue の受け入れ条件が誤っている、または不足している
- 外部 API（Redash 等）の挙動が調査時の想定と違った

**メモの時点では判断しない。** 事実と、どこで引っかかったかだけ書く。整理は 7. で行う。

## 4. 検証する

**すべて通るまで次に進まない。**

```bash
gofmt -l .        # 出力が空であること
go vet ./...
go build ./...
go test ./...
```

落ちている状態で PR を出さない。通らない理由がある場合は PR を出さずユーザーに報告する。

受け入れ条件のうち満たせなかったものがあれば、**満たせなかったと明示する**。チェックを付けない。

## 5. `/simplify` で整理する

**セルフレビューの前に、まず自分の書いたコードを整理する。**
4. の検証は「動くか」しか見ておらず、重複や過剰な抽象は落ちない。

```
/simplify
```

`/simplify` は品質のみを見る。**バグは探さない**ので、これで 6. を省略してはいけない。

- 提案された整理を適用する
- 適用したら **4. の検証をやり直す**。整理が挙動を変えていないことを確認する
- Issue のスコープ外にまで手を広げる提案は**適用しない**。別 Issue にする

## 6. `/code-review` でセルフレビューを通す

**PR を出す前に1回通す。** 機械が見つけられる指摘を人間のレビュアーにさせない。

```
/code-review high
```

`high` 以上は網羅性が上がる代わりに**不確かな指摘も混ざる**。混ざる前提で1件ずつ判断する。

**実行は1回だけ。** 修正後に再実行して収束を待つことはしない。
残りは人間のレビュアーに任せる。

### 指摘は1件ずつ判断する

| 指摘の性質 | 対応 |
| --- | --- |
| 実バグ・`.claude/rules/go-architecture.md` 違反 | **直す。** 直したら 4. の検証をやり直す |
| 誤検知、または意図があってそう書いている | **直さない。** なぜそう書いているかをコードのコメントか PR 本文に残す |
| 正しいが Issue のスコープ外 | **直さない。** 別 Issue に切り出す |

**指摘を判断せずまとめて適用しない。** レビューは判断の材料であって判断そのものではない。
`--fix` は全件に同意し終えた場合にだけ使う。

指摘に対応してテストを足したり直したりした場合も、**受け入れ条件のチェックは実際に満たしたものだけ**に付ける。

修正の量が多く、判断に迷う指摘が残る場合は、**その事実を PR 本文とユーザー報告に書く。**
黙って抱えない。

## 7. 実装 PR を出す

```bash
git push -u origin <branch>
gh pr create --title "..." --body-file -
```

PR 本文に含めるもの：

- `Closes #$ARGUMENTS`
- 受け入れ条件のチェックリスト（実際に満たしたものだけチェック）
- **設計上の判断をした箇所**。ADR に書かれていない判断を下したなら必ず書く
- 満たせなかった条件と、その理由
- 検証結果（テストの実行結果）
- **`/code-review` で出た指摘のうち、直さないと判断したものとその理由**（誤検知は書かなくてよい）

レビュアーが確認すべき点が分かる本文にする。差分を読めば分かることは書かない。
**指摘を全て直した場合、レビューについては何も書かなくてよい。** 通ったことは報告する価値がない。

## 8. 気づきを整理し、設計ドキュメントを更新する

3. で取ったメモを見直し、**それぞれをどこに反映すべきか判断する**。
`/code-review` の指摘で気づいたこと（同じ間違いを繰り返しそうな箇所など）もここに含める。

| 気づきの性質 | 反映先 |
| --- | --- |
| 設計判断を変える／新しく決める必要がある | 新しい ADR を `docs/adr/` に追加 |
| コードの書き方の制約として効かせたい | `.claude/rules/go-architecture.md` を更新 |
| Issue の受け入れ条件が誤っていた | 該当 Issue にコメント、または新規 Issue を起票 |
| 一度きりの詰まり。再発しない | **何もしない。** 実装 PR の本文に書いて終わり |

### 反映しないという判断を恐れない

**気づきが無い回もある。** その場合はこのステップをスキップし、「今回は設計上の変更なし」と報告する。

毎回 ADR を1本足す運用にすると ADR 群が薄まり、本当に重要な判断が埋もれる。
**書く価値があるかどうかを毎回判断すること。**

### 調査してから書く

推測で ADR を書かない。外部の挙動（Redash API、ライブラリの仕様）に関する気づきは、
**必ず一次情報（公式ドキュメント、ソースコード、Issue）を確認してから書く**。
確認した URL は ADR の「参考」節に残す。

### ADR の書き方

- 既存 ADR を**書き換えない**。決定を変える場合は、既存 ADR のステータスを `Superseded by ADR-XXXX` に変え、新しい ADR を立てる
- 番号は既存の続き
- 構成：ステータス / 日付 / 関連 / コンテキスト / 決定 / 結果（得られるもの・支払うコスト）/ 未決事項 / 参考
- **「支払うコスト」を必ず書く。** トレードオフの無い決定は決定ではない
- 決定した理由だけでなく、**採用しなかった選択肢とその理由**を書く

### ドキュメント PR は main から切る

**実装ブランチから派生させない。** 実装の差分が混ざる。

```bash
git switch main
git switch -c docs/issue-$ARGUMENTS-followup
```

PR 本文には「#$ARGUMENTS の実装中に判明した」という経緯を書く。どの実装がきっかけかが分かるようにする。

`Closes` は付けない。Issue を閉じるのは実装 PR の役目。

ドキュメントのみの PR に `/simplify` と `/code-review` は要らない。5. と 6. は実装 PR にだけ適用する。

## 9. 報告する

ユーザーに以下を伝える。

- 出した PR の URL（実装 / ドキュメント）
- 満たせなかった受け入れ条件があればその内容と理由
- **`/code-review` の指摘のうち、直さないと判断したものとその理由**
- ドキュメント PR を出さなかった場合は、その判断理由
- 実装中に気づいたが**今回は反映しなかったこと**があれば、それも伝える

## やってはいけないこと

- `main` に直接コミット・push する
- テストが落ちている状態で PR を出す
- **`/simplify` と `/code-review` を通さずに PR を出す**
- **`/code-review` を2回以上回して収束させようとする**（1回だけ。残りは人間のレビューに任せる）
- **`/simplify` だけで済ませる**（バグは見つからない）
- **レビュー指摘を判断せずまとめて適用する**
- **直さないと判断した指摘を、理由を書かずに黙って捨てる**
- 実装 PR に ADR / rule の変更を混ぜる
- ドキュメント PR を実装ブランチから派生させる
- 受け入れ条件を満たしていないのにチェックを付ける
- 気づきが無いのに ADR をひねり出す
- 一次情報を確認せずに外部の挙動について ADR を書く
- Issue のスコープを超えた変更を実装 PR に含める（気づいたら別 Issue にする）
